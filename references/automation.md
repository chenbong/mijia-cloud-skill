# 普通米家自动化调优

## 审计和定位

1. 导出配置，再用 `scene audit` 查看执行、启用和停用引用。沿嵌套动作查到最终设备，检查否则分支和模板摘要。缺少完整定义时只按已见证据下结论。
2. 按规则 ID 查 `scene history`，把执行时间和当前定义的更新时间对应起来。老版本的错误属于当时的动作。根据列表里的每项错误码判断执行结果，嵌套场景被调用成功后仍要查子场景里的设备动作。
3. 根据请求读取传感器、开关和功率。对照 `device history` 的实际采样，确认传感器是否上报所需的持续时长，以及开关、功率和动作记录发生的顺序。当前显示「无人」仍可能只是传感器漏检。
4. 识别处于待命的规则，以及无引用且在日志覆盖区间内没有执行记录的场景。手动入口可能来自 App、物理按键或语音，日志和家庭内引用各有覆盖边界。按用户授权范围停用、改名或删除。
5. 设备重绑后核对房间和型号。对红外动作，查询主设备挂载的子遥控器及新按键。即使场景文本和主设备 ID 一样，子遥控器也可能已被删除或换 ID。只替换验证过的设备引用和按键，保留原规则 ID、条件及延时。

## 减少规则冲突

- 用同一个手动场景承载需要一起执行的开关动作，让感应、按键和模式入口按需调用。避免多个入口叠加相同动作。手动和自动入口可以共用动作，保留各自的触发和条件。
- 开灯通常采用任一覆盖传感器检测到活动；关灯需相关区域均满足无人条件。若最后达到无人条件的设备可能不同，让它们分别触发同一套复核。门磁开合适合唤起或取消判断，本身无法确定出入方向。
- 把自动化的启用状态当作模式开关时，核对进入、离开、取消和恢复路径。设置不同模式下的互斥开关，防止旧规则被遗留的动作重新启用。延时动作的条件可能只在触发时检查。需要到时重判时，用已验证的独立触发或带条件的后续规则，先用无实物副作用的动作验证链路。
- 制热和制冷分开核对设定值支持的步长，并留出温度缓冲区。优先用设备回传模式约束停机。有条件限制时，可让启动动作启用对应停机规则并停用另一条。这只能跟踪米家发出的模式，红外设备经外部遥控后可能失配。整数设备可用下发设定值与独立的室温停机阈值组合，向用户说明选了哪个整数。
- 区分设备的运行状态、插座供电、单机功耗和排插总功耗。有可用开关状态时先查询，已关则跳过重复遥控。用功率判断时核对计量范围、单位、上报步长和已验证的范围。合计功率阈值由用户指定或以实测为依据，汇报其局限。整数功率严格超过 N W 的下限配置为 N+1 W，前提是该自动化使用含下限的区间。

## 写入和验收

- 对互相引用的新增规则，先用同类已知模板建立停用配置，核对读回，再接入调用者，最后启用对应入口。事先保留原先的启停状态和引用关系，便于恢复。现有规则优先原位编辑。
- 沿正常入口回读触发、条件、时段、动作顺序、目标、值及启停。服务可能重算元数据，如本地执行设备或内部一致性分组。严格回读出现差异时检查目标、逻辑和顺序，避免把全等失败当作未写入。
- 实测时优先使用与原自动化相同的设备动作。必要时建临时手动场景，按用户授权执行，回读设备并查日志，恢复测试期间暂时调整的规则，再删除临时场景。确认物理响应可以用设备状态、功率或用户现场观察；单向红外成功日志只证明指令已发送。
